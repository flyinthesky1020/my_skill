# 社媒爆款与叙事风向调研

> 来源：zero @ Moonshot —— 本文件是 Moonshot 的调研 skill，由 zero 沉淀，转载请注明出处。
>
> 本 skill 由一次「AI 模型×游戏场景」调研的用户逐条校准沉淀，目的是让后续调研零沟通成本。

## 适用与排除

- **适用**：话题风向调研、爆款内容盘点、某产品/模型/技术在社媒上的叙事分析、多平台（X/B站/YouTube/小红书等）内容对比。
- **不适用**：产品 PRD（走 `prd-writing`）；只写文档不调研（走 `feishu-doc-writing`）。

## 总原则

1. **先给框架再动手**：观察维度 + 关键词矩阵先列给用户，确认后再搜；避免「关键词不全漏掉好内容」。
2. **热度门槛**：明显不热的内容不放。参考线是 1000 赞，但不必死卡——一看就不热门的直接排除；低于门槛但构成关键证据的，标注「补录」并说明理由（如方法源头帖、结论的直接证据）。
3. **双证据**：每个案例必须有「截图 + 链接」，截图只截内容卡片（见下文截图规范）。
4. **调研对象是叙事和风向**，不是模型对比打分——除非用户点名要对比。回答的问题永远是：什么在火、为什么火、用户在惊叹/质疑什么。
5. **做一段验收一段**：单平台完成后先给用户验收再继续，不一口气全做完。
6. **找原始出处**：转述帖不算数，追到原作者（例：609 赞转述帖的原帖是 28K 赞的 @mattshumer_）。

## 工作流

### 1. 定框架与关键词

- 观察维度按用户需求拆两层：产品/工程维度（技术栈、case 形态、玩法、视觉）+ 传播/叙事维度（话术、评论惊叹点、官方 vs 社区）。
- 关键词矩阵要覆盖四类，列给用户：
  - 品牌词 × 场景词（"Claude 5.1" game、"GPT-6" game）
  - 泛词（game、Godot、Unity、Unreal、Blender + AI/one-shot，限时间范围）
  - 中文词（"Claude 5.1" 游戏、买量 游戏）
  - 门槛变体（min_faves:1000 / 500 / 100 各跑一遍，避免漏掉中腰部爆款）

### 2. 筛爆款与复核

- **X**：`关键词 min_faves:N since:日期` + `f=top`；提取卡片用 JS 抓 `article` 的 tweetText/User-Name/like/status 链接。
- **B 站**：搜索按播放量排序初筛，再用 `api.bilibili.com/x/web-interface/view?bvid=` 逐条核点赞数（播放高≠点赞高，以赞为准）。
- **YouTube**：按播放量筛，进详情页核点赞。
- 搜完必须复核被拦下的内容：低赞但叙事价值高的可补录；与主题无关的（如 AI 做视频剪辑）明确排除并可向用户说明排除理由。

### 3. 评论区找因果

- 论证的依据来自「用户在评论里夸什么/骂什么 + 作者在发什么」，不凭空分析。
- X 评论区接口经常加载不出来，用搜索绕开：`conversation_id:<推文id> min_faves:20`，`f=top`。
- 高赞质疑声（套壳、slop、反感）和夸赞一样重要，必须纳入。

### 4. 截图规范（最重要，全是踩过的坑）

**构图**
- 只截内容卡片：正文 + 转评赞数据栏。不含评论区、不含页面其他部分、不含侧栏。
- 同主题的多张图做分栏横排（grid），每列图下配一句图注。
- 数据栏（转评赞/播放）必须完整入镜；长卡片先 `cdp Emulation.setDeviceMetricsOverride` 加高视口再截。
- 分辨率不足（卡片 <500px 宽）的糊图一律 2 倍重拍。

**X 后台标签页不加载媒体的解法**
- 现象：daemon 控制的标签在后台时 X 不拉视频流（`videoWidth` 恒为 0），截图媒体区全白。
- 解法：从 `video.poster` / 视频区 `img` / `meta[og:image]` 取官方封面图（`pbs.twimg.com/amplify_video_thumb/...`），新建 `position:absolute`（页面坐标）挂在 `document.body` 的 overlay div 注入封面，等 `img.onload` 后再截。
- 三个关键点：① 不要 innerHTML 注入 React 管理的节点，会被重渲染吞掉；② overlay 必须在隐藏 nav/侧栏/顶栏、完成滚动定位**之后**再注入，否则位置会飘；③ 用 `img.onload` 确认封面真的加载了。
- 头像加载不出来不纠结，用户接受无头像卡片，不要为此卡住流程。但注意：X 头像加载失败时占位有时会渲染成**登录用户自己的头像**（别人的卡片挂着自己的头像，用户明确说"看着好怪"）——自检发现这种情况一律把头像抹成空圆或重截，宁空勿填，不能带病交付。
- 截图可靠性：优先「视口截图 + PIL 按实测坐标裁剪」；CDP `captureBeyondViewport` 的 clip 坐标系不稳定，少用；webbridge `selector:"article"` 的元素截图在 X 上不可靠（会把回复区、发帖框一起截进来），不要用。
- 长卡片（超一屏）：先 `Emulation.setDeviceMetricsOverride` 加高视口（deviceScaleFactor 给 2，给 1 会出 <500px 糊图），**override 后必须重新 measure 卡片坐标再截**（relayout 后旧坐标全飘）；override 跨导航会残留，每次开拍前先 clear。
- 图片 opacity:0：X 的懒加载渐显在后台标签页不触发，img 已加载但 `opacity:0` 渲成白块——截图前对卡片内所有 img 及其父链强制 `opacity:1 !important`，且要在截图前再补一遍（React 重渲染会重置）。
- 彻底不加载的图（img 根本不在 DOM）：用 webbridge `network start` → 打开推文页 → `list` 找 `TweetDetail` GraphQL 请求 → `detail` 里正则提取 `pbs.twimg.com/media/...` 原图 URL，下载后用 PIL 按空白媒体格的实测坐标贴回（多图轮播只贴第一格即可）。X 多图轮播（carousel）只有第一格可见，后面格子在卡片外，别误当 bug。
- 防挂死：`video.play()` 的 Promise 可能永不 resolve，一律 `Promise.race` 加超时；curl 一律 `--max-time`。
- **逐张自检**：画面空白、右侧裁切、顶部被 sticky 头盖住（X 详情页要隐藏 `[data-testid="app-bar-back"]` 的定位祖先）、头像/媒体未加载、Follow/Subscribe 按钮入镜（隐藏 `[data-testid$="-follow"]` / `[data-testid$="-subscribe"]`）、底部多带 Relevant/发帖框（按 reply 按钮所在 `[role=group]` 的下沿裁剪），发现问题立刻重截，不带病交付。
- 写入飞书后必须 fetch 校验：重复 append 会整份双写（命令失败重试前先 fetch 确认是否已写入），编号连续性、grid/列数、图片数逐条核对。

### 5. 沉淀到飞书

结构（以平台调研为例）：
```
一、调研设置（日期、门槛、关键词全清单）
二、一方内容（官方/第一方的动作，前置——它是信号源）
三、X 爆款特质（按主题分节，每节 = h2 主题词 + 一句话论证 + 分栏图组）
四、五、……（B站/YouTube 同构，未做先留裸标题占位）
末位、方法/规律总结（若做：案例分章在前，方法总结放最后一节，不做开场）
```

- 一方（官方/first-party）内容放爆款特质之前；标题用「一方内容」这类主题词，不写「官方一方在 XX 场景的动态」这种长句。
- 一方节的论证只写"有的事实"（征集了什么、多少投稿、里面有什么好 case），不写对比修辞，不写"谁没做什么"的负向判断（如"Anthropic 官方缺席"这类对比分析会被删）。

写作规则（用户逐条校准过，详见 `feishu-doc-writing`）：
- 节标题只写主题词（2~8 字），不写判断句：「Blender + 游戏」「经典IP 复刻」「光影材质 + 2.5D 视角」。
- 论证一句话，从用户/观众视角写因果，大白话，不带「论证：」前缀，不用比喻修辞。
- 图组即论据：分栏横排 + 图注 `图 N｜内容主标题（数据 · 链接）`，引用块格式，编号连续；**不单列论据列表**。
- 案例总表如果和图组信息重复就删掉，不保留。
- 反面案例（没跑出来的类型）文字提一句即可，不专门放图。
- 标题能一个词就不要两个词：「实测 + 祛魅」被改成「实测」，不带对立结构。
- 评论区的因果直接引原话，不写叙述包装：用「好评："xx"」「差评："xx"」各占一行，用户把"评论区一边惊叹…一边吐槽…"整句改成了这种两行式。

### 6. 校准与防覆盖

- 用户改过文档后，必须重新 `docs +fetch` 读全文，逐条对比「我写的 vs 用户改的」，归纳成规则再继续；新规则补进 `feishu-doc-writing` SKILL.md 或本文件。
- 后续任何编辑前，先拉线上全文核对用户手工修改过的地方，**绝不覆盖用户修改**。
- 批量 str_replace / block 操作后必须逐条验证（编号连续性、分栏完整性）——批量操作出过错乱和丢块，有前科。
- block ID 在每次写操作后都可能失效，永远用最新 fetch 的 ID。

## 用户口味速查（校准记录）

- 一句一行、能删则删；不要「本文档用于……」式开场白。
- 图注写「内容主标题」，不写「@xxx · N 赞」这种纯署名。
- 热度不够的内容不要给位置；接近千赞且是方法源头/结论证据的才可补录。
- 同步关键词清单给用户，避免「你搜的不全」的担心。
- 交代无法验证的事实（如视频源不加载），不糊弄。
- 标题可以带具体判断，优于中性主题词：「完美的IP复刻 > 复杂游戏的低水平复制」「在蹭还没发售的GTA6」「我的世界是基本的bench」「玩游戏」都是用户手改的；但论证区不变，仍是一句一行大白话。
- 偏离「话题场景」的内容坚决删：Fireship 的 AGI 疲劳小节（通用 first look，非游戏内容）被用户整节删除；每节必须扣住调研主题。
- 用户移动/删除整块后不重编号，后续新增图注取下一个未用号接着编（如 X 节 18 复用），不要替他整体重排；用户删图后也允许缺号存在（删 图 44 留缺号，引用悬空不处理）。
- 政治敏感梗图不进文档：涉及现实政治人物的 meme/梗图一律不放（赞数再高也不放），对应文字评论可保留——「按按钮美股全红」高赞评论卡被用户删图留文。
- 方法/规律总结节放文末，不放开头：案例分章在前，「宣发方法」这类总结节被用户整节挪到最后一节；方法节图可复用章节图，并允许独立重新编号（方法节 图 1-18，章节 21-127）。
- 方法节标题写动作化短句，不写名词概括（用户逐条手改）：叫板旗舰→旗舰性能平价价格、匿名悬念→匿名免费上opencode、降价免费→限时降价免费、权威下场→大V科学制图下场、用量作证据→用量打榜、入口与案例→showcase案例、梗与争议→玩梗。
- 对比归因类的「方法」不收，只收可复用打法：「发布节奏」（事件型大招 vs 小步快跑的现象对比）被用户整节删除——方法节每节必须是一种能照着做的打法，不是现象归纳。
- 替换含既有图片的 grid/分栏时，旧图一律用本地 `path` 重新上传，不用 `<img src="token"/>` 复用——用户对此手动重传过图。
- B 站卡片截图：视频页「标题+播放数据行+画面+点赞投币收藏栏」即为内容卡片；前台 tab 视频能加载就直接截帧，不用封面 overlay；视口截图+PIL 裁剪同样适用。
