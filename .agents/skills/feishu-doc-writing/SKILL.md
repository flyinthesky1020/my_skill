# 飞书云工作文档写作（用户风格）

> 本风格提炼自用户对「Office Bench 测试记录」和「AI 模型×游戏场景调研」两篇文档的逐条批改。用户改过的文档必须重新 fetch、逐条对比吸收后再沉淀到这里。

## 适用与排除

- **适用**：测试/评测记录、数据台账、工作方案、复盘、周报、调研记录、多人协作的 tracker 类文档。
- **不适用**：产品 PRD（走 `prd-writing` skill）。拿不准时问一句。

## 一、结构原则

1. **协作区置顶**。高频更新、多人填写的内容（问题记录、待办、留言表）放文档**最前面第一节**，不要埋在文末——打开文档就能直接记。
2. **按主题分 h1 大节，内容归位**。同一主题的所有东西（说明、规则、结果表、附件）收在同一个 h1 下，用 h2 分小节，编号连续（1、2、3……）。不要把同一主题的内容拆散到多处。
3. **占位只留标题**。尚未建设的内容只留一个裸 h1 标题即可。**不要**写规划段落、空表格、"待补充/待上传"占位文字——建好是什么自然会是什么。
4. **规律/方法总结节放文末**。调研类文档：案例证据按对象分章在前，规律、方法、共性总结放最后一节，不做开场。（反例：方法节放开头被用户整节挪到文末。）

## 二、行文原则

4. **一句一行，信息点全拆成列表**。禁止大段落；枚举拆成列表，子枚举拆成子列表。
   - ❌ `原始文件：全部来自互联网真实公开文件（GitHub / 政府公开附件 / 官方示例数据）`
   - ✅ `原始文件：全部来自互联网真实公开文件` + 子列表三行：`GitHub` / `政府公开附件` / `官方示例数据`
5. **不写元描述和引导语**。开头不要"本文档用于记录……"的 callout/总览段；正文里不要"见总表 X 列""如下表所示""需要注意的是"这类指引句。读者自己会看。
6. **不造术语，用口语**。说"问题"不说"轴"，说"叠加"不说"维度组合"。专业缩写保留，但自造概念一律翻成大白话。
7. **能删则删**。每个句子问一遍：删掉会损失信息吗？不会就删。修饰语、重复信息、礼节性句子全删。
8. **论证一句话，从用户/读者视角写因果**。调研/分析类段落的"为什么火/为什么有问题"只写一两句大白话，不带"论证："前缀，不用比喻修辞（❌"3D 是社媒上唯一的震撼货币" → ✅"给到提示词或参考图，让用户直观感觉到做一款精良游戏成本很低"）。因果要回到评论区和作者原文里找：用户在评论里夸什么/骂什么，作者发了什么，就是因果的来源，不凭空分析。只写"有的事实"（征集了什么、多少投稿、里面有什么好 case），不写"谁没做什么"的负向对比（❌"Anthropic 官方缺席，游戏全靠社区自发"）。
9. **图组即论据，不单列论据列表**。分栏图 + 一句图注就是证据，不要再跟一列"论据一二三"列表；有独立信息源的评论金句可以揉进那句论证里，不另起列表。

## 三、标题与编号

10. **标题极简**：`产品名 + 用途`，如「Kimi Office Bench 测试记录」。不带括号补充说明（❌「Office Bench 插件测试记录（Word / Excel / PPT · 中国区）」）。
11. **节标题只写主题词，不写判断句、不带括号注释**：2~8 个字说清是什么即可（✅「Blender + 游戏」「经典IP 复刻」「光影材质 + 2.5D 视角」「3. 难度区分度」），结论留给正文那句论证；论证长时拆成多条一行一句的段落，不揉在一个长段里。
12. **方法/规律类节标题写动作化短句，不写名词化概括**：把「怎么做」直接写进标题（用户逐条改写校准）：
   - ❌ 叫板旗舰 → ✅ 旗舰性能平价价格
   - ❌ 匿名悬念 → ✅ 匿名免费上opencode
   - ❌ 降价免费 → ✅ 限时降价免费
   - ❌ 权威下场 → ✅ 大V科学制图下场
   - ❌ 用量作证据 → ✅ 用量打榜
   - ❌ 入口与案例 → ✅ showcase案例
   - ❌ 梗与争议 → ✅ 玩梗
13. **编号连续**：h1 用「一、二、三」，h2 用「1. 2. 3.」，图注用「图 1、图 2……」，跳号/断号要修；但**用户删过图之后允许缺号存在，不要替他整体重排**（用户删 图 44 后留缺号，正文引用悬空也不处理）。

## 四、表格

13. **协作表格列要少而明确**，留空行让人直接填；日期等示例值可以预填第一行做格式示范。
14. **规则/框架类表格**直接给完整对照（维度、权重、档位），不另配解释段落；公式、折算规则单独一行跟在表后。
15. **表格与图组信息重复就删表**。案例总表如果只是把分栏图组里的作者/数据/链接再列一遍，整个表删掉，不保留冗余。

## 五、图片与图注

16. **同主题的图用分栏（grid）横排**，2~4 列，不要整宽竖排堆图；每列图下配一句图注。
17. **图注格式**：引用块，`图 N｜内容主标题（数据 · 链接）`。写内容主标题（这张图讲的是什么），不写「@xxx · N 赞」这种纯署名；每条都必须带可点链接。
18. **图注编号连续**，增删图之后全章重排，检查不重不漏。
19. **反面案例不放图**。没跑出来/效果差的类型在论证里提一句即可，不专门给图位；热度明显不够的案例同样不给图位。
20. **政治敏感梗图不放**。涉及现实政治人物（无论褒贬、无论赞数多高）的梗图、meme 一律不进文档；对应的文字评论可以保留。（反例：高赞评论配「领导人按按钮」梗图，被用户删图留文。）

## 六、编辑纪律

20. **改前先拉线上全文**。任何编辑之前 `docs +fetch` 读当前文档，核对用户手工修改过的地方；**绝不覆盖用户修改**，用户的版本是基准。
21. **block ID 只用最新的**。每次写操作后旧 ID 可能失效，下一步操作前重新 fetch 取 ID。
22. **批量写操作后逐条验证**。str_replace / block_replace 批量执行后，必须 fetch 验证编号连续性、分栏完整性、图片数量——批量操作出过错乱和丢块，有前科。
23. **写操作后必须 fetch 验证**：结构、图片、编号、位置符合预期才算完成；不满足就基于最新内容继续修，不沿用上一轮状态。

## 交付前自查清单

- [ ] 协作/高频填写区在文档第一节
- [ ] 没有任何"本文档用于……"式开场白
- [ ] 全文找不到超过 3 行的段落
- [ ] 占位章节只有标题，无规划文字、无空表
- [ ] 节标题只写主题词，无判断句、无括号注释，编号连续
- [ ] 论证都是一句话大白话，没有比喻修辞，没有"论证："前缀
- [ ] 没有"论据一二三"列表，证据都在分栏图组和图注里
- [ ] 图注全部是「图 N｜主标题（数据 · 链接）」，编号连续不重不漏
- [ ] 表格没有和图组重复的，重复的已删
- [ ] 用户手工修改过的地方原样保留
- [ ] 每个句子删掉都不损失信息的已删干净

## 风格校准流程

每次代写/代改飞书文档后，主动请用户审阅；用户改完必须重新 `docs +fetch` 读取全文，逐条对比「我写的 vs 用户改的」，把新差异归纳成规则补进本 SKILL.md 对应章节。
